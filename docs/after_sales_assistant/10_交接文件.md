## 3. 产品逻辑（业务侧，后续 Agent 不要搞反）

- 同一对话入口；用户提问后先做意图（查知识 vs 查数据）。
- 默认单边：多数问题只走一条支路，不默认「知识库 + 数据库」双答拼在一起。
- 查知识：知识库检索 + AI，依据文档片段回答 3C 数码售后规则、保修政策、型号差异、故障排查、维修渠道等。
- 查数据：AI 生成 SQL → 自定义工具执行 → AI 把 JSON 结果说成自然语言；工具负责真查库，不是多余步骤。
- 当前主线只做查知识这一支路的 3C 强领域化二开，重点是分块、检索/重排、弱证据拒答、合规约束；Text2SQL 仅维护现状。
- 扩展项可以写进规划，但不应盖过主线。当前更适合写进路线图的扩展项包括：型号-规则自动匹配、轻量槽位继承、工单自动生成、外部工具对接。

### 4.3 当前已锁定的业务结论

- 用户现在最看重的是「二开价值能否被看见」，因此主线必须强调强领域化，而不是泛客服场景
- baseline 与最终版应尽量使用同一套知识库和同一套题集，便于清晰体现前后差距

### 4.4 本窗口新增有效结论（向量化 + 题集）

- 向量化失败根因已定位：不是 Celery 没开、不是数据库未导入，核心是 embedding 接口超时导致段落级失败（`APITimeoutError: Request timed out`），并发高时更明显。
- 当前知识库使用的向量模型链路：`model_openai_provider` + `baai/bge-m3` + `https://api.ppio.com/openai/v1`（OpenAI 兼容网关）。
- 已完成源码修复：`apps/models_provider/impl/openai_model_provider/model/embedding.py` 增加了超时与重试兜底（timeout=120s，本地指数退避重试），目标是降低批量导入时的偶发失败。
- 运行现象判断标准已明确：任务“慢”不等于“卡死”。若 `para_pending` 持续下降即为在推进；若 `para_fail` 增长，通常是网关抖动后的可重跑失败。
- 本窗口关于“是否必须开 VPN”的结论：不是必须。是否稳定主要取决于所用网关质量与并发设置；若走国内稳定 embedding 服务通常更稳。
- 题集清洗已形成可用 baseline 版本结论：可直接使用 `cases_300_评测脚本版_清洗版_v3.json` 跑正式 baseline。v4 失败是阈值判定条件触发，不是文件不可用。
- 题集 v3 当前状态：结构完整、可读取、非 expect 字段未被污染；仍有少量弱词残留，属于后续精修项，不阻塞 baseline 开跑。
- 下一窗口第一动作建议固定为：先用 `cases_300_评测脚本版_清洗版_v3.json` 跑 baseline，得到首轮指标后再做少量定点人工修补并沉淀 `v_final`。

## 5. 已暴露的「坑」（后续排障用）

- YAML：`REDIS_PASSWORD` 等键，冒号后必须有空格，否则解析失败。
- Text2SQL 链路：第一个 AI 若把 SQL 包在 Markdown 代码块里传入工具，工具校验可能失败；画布侧需收紧提示词，更稳的做法是在 `safe_pg_tool_for_maxkb.py` 入参侧做剥离（见 08 第二节）。
- 意图节点：分类没有单独「例句」字段时，长说明写在同一「分类 content」框即可（会进入平台内置分类提示模板）。
- 知识问答慢：单题常在 3-20 秒，个别题超过 60 秒。慢不全是分支多，还包括主回答扩写过长、检索输入过长、模型/供应商抖动等。
- 3C 场景下如果不把品牌、型号、SKU/SN 这类结构化字段纳入检索链路，极易出现召回错型号、错规则的问题。
- 高风险问题仅靠 prompt 很难稳住，尤其是保修资格、拒保判定、维修费用、时效承诺等场景，后续必须在系统层做约束。
