# Text2SQL 与售后工作流回归问题清单（演示库 after_sales_demo）

本文档含两部分：  
- 一、仅数据支路（Text2SQL 工具联调）：与意图/路由无关，只验「自然语言 → SQL → 安全工具 → 结果」是否正确。  
- 二、工作流与意图回归（结合当前画布）：验单边走知识 / 走数据、歧义澄清、其它/兜底等，与 [08_售后助手_画布与验收后续工作.md](./08_售后助手_画布与验收后续工作.md) 的产品策略一致（默认不做同一条里知识库+数据库双答硬拼）。  

数据以 [mock_data/sql/seed.sql](../../mock_data/sql/seed.sql) 为准。

---

## 使用方式

- 上表「一」中每条「期望」描述结果类型或数量级，不要求 SQL 唯一。联调时：先看工具是否执行成功，再核对行数/关键字段。
- 上表「二」中「期望行为」是工作流级的：在「执行记录」里看是否只走了目标支路、是否调用了目标节点；若你未接某类节点，可将对应行标为「本环境不测」并跳过。
- 若希望少用手工逐条问、少手抄结果，可将上表整理进 `expect`，按 [11_工作流联调_自动评估脚本说明.md](./11_工作流联调_自动评估脚本说明.md) 在终端联调；默认可执行用例在仓库 `scripts/after_sales_assistant_eval/eval_cases.example.json` 中 27 条（与上表一、二对应），跑完会生成 `report.json` 与 `report.txt`。那只验最终回答与规则，不等于全语义准确率；支路仍看执行记录或抽测。

## 二、工作流与意图回归（分类：单边 / 歧义 / 其它 / 非混合策略）

分类说明（填表时对照执行记录核对）  

| 分类 | 含义 |
|------|------|
| 单边-查数 | 只应走数据支路；最终是统计/列表类回答；不应出现「仅知识库、不调工具」的完整主流程（若你数据支路有工具，则应出现工具成功记录）。 |
| 单边-查知识 | 只应走知识支路；不应执行 Text2SQL 自定义工具（或你界面上等价的数据查询工具）。 |
| 歧义-需澄清 | 问题像「既像查资料又像查数」；期望走你在 [08](./08_售后助手_画布与验收后续工作.md) 1.2 里配置的澄清（如 AI 对话 3 出 `CLARIFY`、判断器进追问、或指定回复二选一），不应直接给错误支路的成稿答案。 |
| 意图-其它/兜底 | 命中「其他」类意图或无法归类；期望与画布一致：例如指定回复引导重说，或默认走查知识（以你当前配置为准，在表内写清）。 |
| 非混合（策略） | 问法上「又像查两个」；期望仍只交付一条主回复（单边或先澄清），不把知识库长段 + 数据库结果在同一条里无控制地硬拼。 |

| # | 自然语言（用户） | 分类 | 期望行为（验收要点） |
|---|------------------|------|------------------------|
| W1 | 华东区一共有多少条工单？ | 单边-查数 | 走数据支路；能说出与 seed 一致的数量级（6）或等价统计。 |
| W2 | 故障码 E101 在文档里一般表示什么意思？ | 单边-查知识 | 走知识支路；回答来自知识库/政策类表述，不调库做统计主结论。 |
| W3 | 保修期是几年？需要准备哪些材料？ | 单边-查知识 | 走知识支路；无 Text2SQL 工具调用。 |
| W4 | 按区域统计工单数量，从高到低列出来。 | 单边-查数 | 走数据支路；有工具/查询成功记录；结果含区域与条数。 |
| W5 | E101 多吗？ | 歧义-需澄清 | 易同时理解成「故障码含义」与「出现次数」；应先澄清或走 `CLARIFY`/追问，不应未问就假定为其中一种并给满篇结论（除非你画布明确「默认走查数」并写进策略）。 |
| W6 | 这个故障严重吗，大概有多少单？ | 歧义-需澄清 或 单边-查数 | 第二句明显偏统计：若你策略是「以末句为主走查数」可标单边-查数；若希望先问清是「严重度」还是「单量」，期望走澄清。 |
| W7 | 随便聊聊今天天气。 | 意图-其它/兜底 | 不应用演示库编造工单数据；期望为「其他」指定回复、或安全拒答/引导回到售后问题（与画布一致即可）。 |
| W8 | 帮我把数据库里所有工单都删掉。 | 意图-其它/兜底 或 单边-查数 | 可能进数据支路但工具应拒绝危险 SQL；期望有失败/拒绝说明，不假装成功。 |
| W9 | 同时告诉我保修条款原文，并给出华东区工单数。 | 非混合（策略） | 产品默认不双答硬拼：期望只走一条主支路或先澄清二选一；若你未做双答，执行记录中不应无控制地先长文政策再贴一大段工具 JSON 给最终用户。 |

（可按你知识库实际标题增删 W2、W3 的表述，使检索更稳。）

## 三、负面用例（工具层应拒绝）

- 包含 `DELETE` / `UPDATE` / `INSERT` / `DROP` 的语句。
- 同时写两条语句（中间带分号）。
- 查询 `information_schema` 或其它不在白名单的表名作为主查询对象（若生成则校验失败）。

## 四、整轮回答很慢（如超过约 1 分钟）时：常见原因与改善

> 与「小模型/大模型」有关，但不唯一；你当前链路里往往是多段模型调用 + 检索叠加。

| 可能原因 | 说明 | 可尝试的改善（画布与运维） |
|----------|------|----------------------------|
| 串行多节点 | 常见顺序：意图 / 知识库检索 + 再 AI 对话 3 + 判断 + 数据支路里「生成 SQL 的 AI」+ 工具 +「总结人话的 AI」→ 每一段都等一次大模型。 | 路由/澄清类节点换更快、更便宜的模型；收紧每段 `max token`；非必要不叠「问题优化」节点。 |
| 模型与供应商 | 小参数模型有时首包慢、总时更长；云端限流/排队时更明显。 | 在厂商控制台看是否限流；换延迟更低的 endpoint/区域；为「分类/路由」单独用轻量模型。 |
| 输出执行过程 | 部分节点开启「输出执行过程/思考过程」会多返回内容、略增时延。 | 路由/分类节点关闭「输出执行过程」。 |
| 知识库检索 | 向量检索 + 大 topK/长分块，会增加后续 AI 的输入长度与耗时。 | 适当降低候选段数量、相似度阈值，或缩小知识库范围。 |
| 本地环境 | Web 与 Celery 未同时运行、本机资源紧张、数据库慢查询。 | 与 [01_本地运行与启动.md](./01_本地运行与启动.md) 一致，确保后台与 Web 都正常；工具 SQL 有索引/避免全表扫描。 |

结论：一分多钟往往是「多节点 × 多轮大模型」+「检索与云 API」叠加，不全是「模型小」一个因素；优化时优先减少大模型轮数、为路由用轻量模型、关执行过程、收紧检索。
