# 工作流联调与自动评估脚本

本页说明评测脚本怎么跑、产出哪些文件、双指标怎么读。配套规则定义见 `15 二开规划` 第 3.5 节、第 5 节。

可执行文件、用例样例、本地密钥放在代码目录，不放本 `docs` 下，原因是要与 Python 虚拟环境、`.gitignore` 里的 `local_secrets`、同目录相对方便运行。

- 代码与数据目录：`../../scripts/after_sales_assistant_eval/`
- 同目录主要文件：
  - `run_eval.py`、`one_click.py`：评测入口
  - `ecom_first_batch_cases.json`：当前主线题集（电商售后 300 题，Day 2 落盘后存在）
  - `first_batch_cases.json`：3C 阶段历史题集 30 题，已归档不再跑
  - `local_secrets.example.json`：复制为 `local_secrets.json` 并填密钥后使用，勿提交

能做什么：按用例 JSON 里的一批问题自动发问，对最终回答做关键词子串规则验收 + LLM-as-judge 语义打分，统计耗时与拒答正确率，生成 `report.json` + 可读的 `report.txt`。

不能做什么：不做"全语义准确率"等价判断；支路是否走对要看平台执行记录。LLM-as-judge 也只是参考，不是真值。

## 一键（推荐）

1. 在 `scripts/after_sales_assistant_eval` 下放置 `local_secrets.json`（从 `local_secrets.example.json` 复制，已加入 .gitignore）。
2. 若尚无 `ecom_first_batch_cases.json`，按 Day 2 输出物准备好。
3. 在 WSL 终端：

```bash
cd /home/tlx/projects/MaxKB/scripts/after_sales_assistant_eval
../../.venv/bin/python one_click.py --cases ecom_first_batch_cases.json
```

4. 看结果：终端有 PASS / FAIL 与一段汇总；同目录生成 `ecom_first_batch_report_roundN.json` 与 `.txt`。文首为「汇总」：关键词通过率、LLM-as-judge 平均分、拒答正确率、各分类未通过条数、未通过用例 ID 列表；正文为每题问题与完整回答。UTF-8。报告文件已 .gitignore 不提交。

`local_secrets.json` 只填 MaxKB 本应用下创建的 API 密钥（`application-` 或 `agent-` 开头），与第三方聊天模型、其它云厂商的密钥不是同一套。

## 最简手跑（不通过 one_click）

1. 在应用里创建 API 密钥，记下为 `application-` 或 `agent-` 形式。
2. 应用 ID：在「高级编排 / 工作流」编辑页地址栏，路径形如 `.../admin/application/workspace/这串UUID/workflow`；`workspace` 为路由固定段，其后 UUID 即应用 ID。
3. 终端中：

```bash
cd /home/tlx/projects/MaxKB/scripts/after_sales_assistant_eval

export MAXKB_BASE="http://localhost:8080"
export MAXKB_CHAT_PATH="/chat"
export MAXKB_APP_ID="你的应用ID"
export MAXKB_API_KEY="你的 application- 或 agent- 密钥"
export JUDGE_MODEL_BASE="judge 模型的 API 地址"
export JUDGE_MODEL_KEY="judge 模型的 API 密钥"
export JUDGE_MODEL_NAME="judge 模型名（必须与 MAXKB 应用里的回答模型不同源）"

../../.venv/bin/python run_eval.py ecom_first_batch_cases.json -o ecom_first_batch_report_round1.json
```

`config.yml` 未改 `CHAT_PATH` 时保持 `/chat`。勿把密钥写进 `run_eval.py` 源码；可用同目录 `local_env.sh`（勿提交）存 `export` 后 `source`。

## 用例 JSON 字段

每条题包含：

```
{
  "id": "EC001",
  "category": "退款退货 / 物流 / 订单 / 商品 / 账户支付 / FAQ / 应拒答 / 边界",
  "question": "...",
  "expect": {
    "answer_contains_all": ["..."],
    "answer_contains_any": ["..."],
    "answer_not_contains": ["..."],
    "case_insensitive": true,
    "judge_prompt": "请按 0-2 分给下面的回答打分..."
  }
}
```

- `answer_contains_*` / `answer_not_contains` / `case_insensitive`：关键词规则部分，沿用旧规则不变
- `judge_prompt`：LLM-as-judge 提示词模板，必须明确"0 不相关、1 部分正确、2 完整正确"三档；不要让 judge 自由发挥
- 应拒答用例：`expect` 里直接写 `should_refuse: true`，脚本据此判定是否走了固定拒答模板
- 边界题用例：`expect` 里两套规则都允许更宽（部分给分），属于"半正确也算过"的灰区

## 双指标含义

- 关键词通过率 = 满足 `answer_contains_*` / `answer_not_contains` 规则的条数 / 总条数
- LLM-as-judge 平均分 = 所有题打分均值（0-2 分）
- 拒答正确率 = 应拒答用例中实际走拒答模板的比例

简历讲"双指标对照"指的是关键词通过率 + LLM-as-judge 平均分两列；拒答正确率作为单独指标列出。

## judge 模型选用约束

- 必须与回答模型不同源：避免同模型自评偏差
- judge prompt 必须写在脚本配置文件里，不允许动态生成或运行时拼接
- 报告里要写明本次跑用的 judge 模型名与 prompt 版本号，便于复现
