# 售后助手：画布与验收后续工作

> **本文范围**  
> 只写你需要在 **MaxKB 画布 / 后台界面** 里亲自完成的事项，以及每项对应的**业务逻辑**（解决什么问题、用户感受到什么）。  
> **不写** 具体代码实现；若某条涉及「自定义工具 Python」等代码改动，文中仅标注为 **「可交给 Cursor Agent 按仓库实现」**，由你另开 Agent 任务完成。  
> 同目录文档编号与阅读顺序见 [00_文档阅读顺序.md](./00_文档阅读顺序.md)（本文为 `08`）。

你已完成的 **方案 B（单边意图分流 + 知识/数据两支路）** 不在本文重复说明，见 [07_画布操作流程.md](./07_画布操作流程.md)、[06_单边意图分流_工作流配置.md](./06_单边意图分流_工作流配置.md)。

## 一、业务与体验（优先）

目标：让用户觉得助手**听得懂、分得清、不乱答、必要时愿意多问一句**。

### 1.1 意图分类写清楚（仍在「意图识别」节点里完成）

| 业务在干嘛 | 为什么要做 |
|------------|------------|
| 每个意图分支的 **分类说明**（界面里每个意图只有一格文字，但可写长）里，写清 **定义 + 典型问法 + 边界**，减少「查数问题走进知识库」或相反。 | 模型只靠「查知识」「查数据」四个字容易误判；写厚后单边分流更稳。 |

**你在画布上要做的：**

- 打开 **意图识别** → **意图分类**里每一项的输入框。  
- **查数据**：写明含「多少条、统计、排名、占比、按地区/状态筛选、演示库、工单表」等说法的归此类；可抄几条 [05_Text2SQL回归问题.md](./05_Text2SQL回归问题.md) 里的问法当例句。  
- **查知识**：写明含「政策、保修、步骤、故障码含义、SOP、安装校准」等归此类；给几条典型问法。  
- **其他**：写明无法归类时的默认行为（与产品一致：例如默认走查知识更安全，或走指定回复提示用户说清一点）。

**注意：** 该节点底层要求模型按固定 JSON 返回分类结果，**不要**在这一格里写破坏 JSON 输出格式的长指令；只写「每类是什么、包含哪些说法」即可。

---

### 1.2 歧义澄清（画布：加节点 + 写提示或固定话术）

| 业务在干嘛 | 为什么要做 |
|------------|------------|
| 用户一句话可能既像查资料又像查数（例如「E101 多吗」），不硬猜，**先澄清再单边执行**。 | 减少误进支路后的「答非所问」和投诉感。 |

**你在画布上可以怎么做（择一或组合，按你产品接受度）：**

- **做法 A**：在意图识别之后、两条支路之前，增加 **「AI 对话」只做澄清**：输出简短二选一或追问缺省信息；再用 **判断器** 根据输出走向知识或数据支路（维护成本略高）。  
- **做法 B**：在 **「其他」** 或低置信场景，用 **「指定回复」** 直接提示：「您是想了解含义还是统计数量？请补充产品型号或时间范围。」  
- **做法 C**：暂不单独节点，仅在 **意图分类说明** 里写清边界（实现成本最低，效果介于两者之间）。

---

### 1.3 拒答与兜底（画布：条件 + 指定回复 / AI）

| 业务在干嘛 | 为什么要做 |
|------------|------------|
| **知识支路**：检索结果为空或极弱时，不编造政策/SOP。 | 避免「没依据硬答」，提升可信度。 |
| **数据支路**：工具返回失败、`ok` 为 false、或结果为空时，不说假数字。 | 与 Text2SQL 工具行为一致，用户体验可控。 |

**你在画布上要做的（思路）：**

- **知识支路**：在 **知识库检索** 与 **最终 AI 回答** 之间，用产品提供的 **判断器 / 分支**（若版本支持「是否命中 / 列表是否为空」类条件），对「无命中」走 **指定回复** 或 **短 AI**：统一话术如「当前知识库未找到直接依据，请补充产品型号或换种问法」。  
- **数据支路**：在 **工具节点** 之后，用分支判断「成功 / 失败」或解析 `ok`（若界面支持引用工具输出字段）；失败走 **指定回复**：「暂时无法查询数据，请稍后再试或检查问题描述」；空结果可走 **指定回复** 或让第二个 AI 在系统提示里要求据实说明「无记录」。  

具体节点名称以你当前 MaxKB 版本为准；核心是 **「无证据不答、失败不乱答」**。

## 二、工程与稳定（画布能做的 + 代码交给 Agent）

目标：减少「偶发能答、偶发不能答」、减少模型输出格式导致的失败。

### 2.1 画布侧：约束第一个「生成 SQL」的 AI（必做、零代码）

| 业务在干嘛 | 为什么要做 |
|------------|------------|
| 让模型 **只输出纯 SQL**，不要 Markdown 代码块、不要前后解释。 | 你已遇到过：SQL 被包在代码块里会导致工具执行失败，第二个 AI 只能说「无法确定」。 |

**你在画布上要做的：**

- 打开 **数据支路** 里 **第一个 AI 对话** 的 **系统提示词**，在现有表结构规则之后，**明确加几条**：禁止代码块、禁止反引号、只输出一条可直接执行的 SQL、首字符须为 `S`（SELECT）等（表述可按你习惯调整）。  
- 可选：将该 AI 的 **温度调低**（若界面提供高级参数）。  
- 可选：关闭 **「输出执行过程」**，避免把中间 SQL 过程混进用户可见回复（若你仍觉得界面展示乱）。

---

### 2.2 代码侧：入参清洗与安全增强（不在本文写实现）

| 业务在干嘛 | 为什么要做 |
|------------|------------|
| 即使用户提示词已约束，模型仍可能偶尔输出 Markdown；在 **工具入参进入校验前** 剥掉外壳，可显著降低失败率。 | 属于「最后一道保险」，和画布提示词互补。 |

**你需要做的：**

- **不**在本文里写代码。  
- 在仓库中打开 **`mock_data/text2sql/safe_pg_tool_for_maxkb.py`**，另开 **Cursor Agent**，说明需求：**对参数 `sql` 在校验前剥离 Markdown 代码块与首尾空白**，并保持现有白名单与安全策略不变。  
- 改完后在 MaxKB **工具调试** 里用「带 Markdown 围栏的 SQL 字符串」测一遍，再在画布上回归你常用问法。

---

### 2.3 工具节点「返回内容」开关（画布上顺手检查）

| 业务在干嘛 | 为什么要做 |
|------------|------------|
| 控制 **是否把该节点输出直接展示给用户**。 | 数据支路最终希望用户主要看 **第二个 AI 的人话**；工具 JSON 若直接展示，体验差。 |

**你在画布上要做的：**

- 打开 **售后 sql 助手（工具）** 节点，阅读 **「返回内容」** 开关说明；一般建议 **工具关、最终 AI 开**（以你界面文案为准）。

## 三、评测与验收（主要在你与文档里完成，不靠画布拖新节点）

目标：证明助手 **「能稳定交付」**，而不是「我演示时碰巧对了」。

### 3.1 扩充并固定「回归问题表」（文档 + 自测）

| 业务在干嘛 | 为什么要做 |
|------------|------------|
| 把典型问法列成表，每次改意图文案或提示词后 **同一批问题重跑**，看是否仍走对支路、回答是否合理。 | 这是你能向他人（或面试）证明「做过质量控制」的凭据。 |

**你需要做的：**

- 在 [05_Text2SQL回归问题.md](./05_Text2SQL回归问题.md) 基础上，**增补**：纯知识问法若干、纯数据问法若干、**边界/歧义**问法若干。  
- 为每一类至少标注：**期望走查知识还是查数据**、**期望行为**（例如：必须出现工具调用 / 不得出现工具调用）。  
- 每次改动画布后，按表 **人工问一轮**（或若日后你用 Agent 写了自动脚本，再交给脚本；脚本实现不在本文写）。

---

### 3.2 上线前自检清单（业务侧）

**你需要做的：** 对照勾选（可打印或复制到你的笔记）。

- [ ] 随机多条「明显查资料」的问法，是否 **只** 走知识支路且 **不** 调数据库工具。  
- [ ] 随机多条「明显查数」的问法，是否 **只** 走数据支路且数字与演示库 **大致一致**。  
- [ ] 故意问模糊句，行为是否符合你在 **1.2** 定的规则（澄清 / 默认走哪边 / 指定回复）。  
- [ ] 知识检索无命中时，是否 **不编造** 且话术友好。  
- [ ] 工具失败或 SQL 非法时，是否 **不乱报数字** 且有兜底说明。  
- [ ] **保存并发布** 后，用访客/新会话再测一遍，避免只看到本地缓存的旧行为。
