# 企业内部办公 Agent 实施蓝图

## 1. 文档目标

这份文档不是概念方案，而是面向实际开发的施工蓝图。

目标有 5 个：

1. 把项目定位正式锁定为内部 Web 系统 + MaxKB 二开
2. 把一期范围锁定到可以在 4 到 6 周内做出可演示版本
3. 把核心数据对象、页面、接口、模块边界提前定死
4. 把 Claude Code 多模块并行开发方式说明白
5. 把部署方式、通知渠道、模型接入方式定成当前最稳方案

## 2. 总体落地结论

### 2.1 项目形态

本项目一期建议做成公司内部 Web 系统，不优先做小程序，也不单独再起一套新技术栈。

推荐形态：

- 管理端：给老板、部门负责人、管理员使用
- 员工端：给普通员工提交日报、查看任务、上传文件、使用问答能力
- AI 能力层：继续复用当前 MaxKB 中对你项目有价值的知识库、对话链路、文件检索等能力

当前仓库里已经存在的复用入口：

- 总路由挂载：`apps/maxkb/urls/web.py`
- 用户与登录：`apps/users/urls.py`
- 知识库与文档处理：`apps/knowledge/urls.py`
- 文件回传：`apps/oss/retrieval_urls.py`

### 2.2 为什么不建议另起项目

因为你这个项目的核心不是“做一个新网站”，而是“把文件、用户、任务、AI、通知串起来形成办公闭环”。

如果另起项目，会重复建设下面这些能力：

- 登录和权限
- 文件上传和源文件访问
- 文档解析和知识库导入
- AI 工作流编排
- 定时任务
- 模型接入

这些当前仓库已经有可复用基础，所以一期最优路径是继续在当前仓库内按新业务模块扩展。

### 2.3 不是保留完整 MaxKB，而是做精简版新项目

这里要特别说明一件事：

推荐继续基于 MaxKB 二开，不等于保留 MaxKB 原本所有功能。

你这个新项目最终目标应该是：

- 保留你需要的 3 类核心功能
- 保留这些功能必须依赖的底层能力
- 删除或关闭与项目无关的原生功能

也就是说，最终交付物应该是“基于 MaxKB 底座裁剪出来的办公 Agent 精简版”，而不是“把原版 MaxKB 全部保留下来再叠加新功能”。

明确保留的底层能力：

- 登录与基础权限
- 文件上传与文件访问
- 知识库导入与文档问答
- 对话生成链路
- 你项目真正需要的定时任务能力

明确不保留或不对外暴露的原生能力：

- 多模型管理界面
- 与你项目无关的通用触发器页面
- 与你项目无关的工具市场、工作流搭建入口
- 与你项目无关的原生应用管理页面
- 其他不服务于会议纪要、日报任务、文件问答、受控改表的功能入口

但“删功能”这件事不能一上来粗暴删除全部源码，正确顺序应该是：

1. 先锁定你自己的业务模块和依赖链
2. 先从前端菜单、路由、后端接口暴露层隐藏无关功能
3. 等你的办公 Agent 主链路稳定后，再做源码级裁剪
4. 最后清理数据库表、前端页面、后端路由和无用依赖

这样做的原因很简单：

- MaxKB 原有模块之间存在依赖关系
- 一开始就大删代码，容易把登录、文件、知识库这些底层能力一起删坏
- 先“关入口再清源码”是更稳的精简方式

## 3. 一期范围锁定

一期只做 3 个闭环，不扩到更多泛化能力。

### 3.1 闭环一：会议纪要

业务目标：

- 把腾讯会议转写文本快速变成结构化纪要
- 在输出前识别疑似错误术语并向用户确认
- 自动提取会议中的任务项和负责人
- 最终输出 PDF 并归档

一期必须实现：

- 粘贴会议文本
- 术语纠错与确认
- 结构化纪要生成
- PDF 导出
- 任务抽取
- 纪要归档与检索

一期暂不做：

- 会议录音直接上传转写
- 腾讯会议官方 API 深度接入
- 多会议室自动抓取

### 3.2 闭环二：日报与任务

业务目标：

- 员工下班提交日报
- 系统提取任务项并形成任务状态池
- 第二天自动给员工展示自己的待办和方向建议

一期必须实现：

- 上传日报 PDF
- 支持补录结构化日报
- 自动提取任务项
- 任务状态只有 3 个：进行中、挂起、已完成
- 同一任务同名日报文件上传时替换旧版本
- 生成个人今日任务提醒
- 结合前一天会议纪要生成方向建议

一期暂不做：

- 复杂甘特图
- 多级审批流
- 自动绩效评分

### 3.3 闭环三：文件问答与自然语言操作

业务目标：

- 上传测试报告、出入库表、Excel、Word、PDF 后，支持直接问答
- 问答时能返回命中的原始文件
- 对结构稳定的业务表支持自然语言查改

一期必须实现：

- 上传 Excel、Word、PDF
- 测试报告和说明文档进入知识库问答链路
- 回答结果附原文件链接
- 可直接打开原文件
- 先选 1 张高频业务表做自然语言查询
- 在这 1 张表上支持受控修改，且必须确认后执行

一期暂不做：

- 所有表单统一低代码化
- 任意 Excel 自动转任意数据库结构
- 对所有文档都支持写入修改

### 3.4 一期验收口径

只要一期能稳定跑通下面 6 条，就算达到第一阶段目标：

1. 会议文本可以生成纪要 PDF
2. 会议中的任务项可以落到任务池
3. 日报 PDF 可以抽取为任务状态
4. 员工登录后能看到自己的今日任务提醒
5. 上传的测试报告可以问答，并能打开原文件
6. 物料出入库表能完成自然语言查询和一次受控修改演示

## 4. 产品与权限设计

### 4.1 角色定义

一期固定 4 类角色：

- 超级管理员
- 系统管理员
- 部门主管
- 普通员工

权限边界：

- 超级管理员：系统配置、词典配置、账号管理、所有数据可见
- 系统管理员：业务配置、文件管理、账号创建、通知配置
- 部门主管：查看本部门纪要、日报汇总、任务汇总
- 普通员工：只看自己的任务、日报、允许访问的共享文件

### 4.2 登录和绑定不冲突

系统需要同时维护两类身份信息：

1. 系统身份
- 用户名
- 密码
- 角色
- 部门

2. 通知身份
- 邮箱
- 手机号
- 企业微信 user_id
- 飞书 open_id

也就是说：

- 登录靠账号密码
- 推送靠外部渠道绑定信息
- 一个员工记录可以同时拥有多个通知字段

这两层不会冲突，反而必须分开。

## 5. 后端模块划分

## 5.1 推荐目录策略

为了减少对现有系统的破坏，一期建议新建一个独立业务域应用：

- `apps/office_agent/`

再在这个应用下拆子目录：

- `apps/office_agent/models/`
- `apps/office_agent/api/`
- `apps/office_agent/service/`
- `apps/office_agent/tasks/`
- `apps/office_agent/serializers/`
- `apps/office_agent/views/`
- `apps/office_agent/constants/`

这样做的原因：

- 你这次是新增办公业务，不是改造原有售后业务
- 新业务模型明显独立，和 `users`、`knowledge`、`trigger` 更适合做“复用关系”，不适合继续堆在原应用里
- 后面如果继续扩会议、日报、表格 AI 操作，也更好维护

### 5.2 与现有仓库的关系

推荐复用关系如下：

- `apps/users`
  - 继续负责登录、基础用户信息、权限鉴权
  - 新增员工扩展信息时，使用 `office_agent` 补业务扩展表，不要大改用户核心表

- `apps/knowledge`
  - 继续负责文档上传、切分、嵌入、检索、源文件下载
  - 测试报告、产品报告、说明文档优先挂到知识库能力里

- `apps/trigger`
  - 不建议作为最终保留的业务模块继续对外暴露
  - 如果早期为了节省开发量暂时复用其底层调度能力，可以只复用底层实现，不保留原生触发器页面和通用能力
  - 最终目标是把你项目需要的提醒调度能力收敛到 `office_agent` 自己的任务模块里

- `apps/oss`
  - 继续负责文件访问和回传
  - 问答结果中的“打开原文件”直接走已有文件访问链路

- `apps/application/chat_pipeline`
  - 继续复用对话链路做会议纪要生成、日报建议、知识问答

## 9. AI 与工作流实现方式

### 9.1 会议纪要链路

推荐按 4 步拆开：

1. 文本预处理
- 清洗无意义口头语
- 标记可能错误的术语

2. 待确认项生成
- 把疑似错误词生成确认问题
- 允许用户逐条确认

3. 纪要生成
- 固定模板输出会议主题、结论、待办、负责人、时间点、风险

4. 任务抽取
- 从最终确认文本中抽任务项
- 直接落到 `meeting_action_item` 和 `task_item`

### 9.2 日报链路

推荐按 4 步拆开：

1. 读取 PDF 或表单内容
2. 标准化成统一日报结构
3. 提取任务项并与已有任务做匹配
4. 结合前一天会议纪要生成今日建议

任务匹配规则建议：

- 先按员工 + 任务标题近似匹配
- 再按日期窗口判断是否延续旧任务
- 匹配成功则更新已有任务
- 匹配失败则生成新任务

### 9.3 文件问答链路

推荐两条链路并行存在：

1. 文档问答链路
- PDF、Word、测试报告进入知识库
- 用户提问后走检索增强问答
- 结果返回引用片段和原文件链接

2. 表格操作链路
- Excel 首次导入数据库
- 自然语言转受控 SQL 或受控工具参数
- 查询直接返回
- 写操作必须先预览后确认

### 9.4 为什么表格写操作不能直接改 Excel

因为直接改 Excel 会带来 4 个问题：

1. 无法稳定并发
2. 难做权限控制
3. 难做审计追踪
4. 容易污染原始文件

正确做法是：

- 原 Excel 作为源文件保留
- 数据库存业务真值
- Excel 只用于导入和导出

## 10. Claude Code 多模块并行开发方案

你后面如果用 Claude Code 开发，不要把整个项目一口气丢给一个会话，而是要拆成“总控 + 子模块”。

### 10.1 总控会话负责什么

主会话只负责 5 件事：

1. 锁定数据模型
2. 锁定接口契约
3. 锁定目录结构
4. 分配子模块任务
5. 做最终合并和验收

### 10.2 子会话拆分建议

推荐至少拆 4 条子线：

1. 子线 A：用户、权限、员工资料、通知绑定
2. 子线 B：会议纪要与术语确认
3. 子线 C：日报、任务池、提醒建议
4. 子线 D：文件问答、原文件回显、表格查询与受控修改

### 10.3 并行开发的先后顺序

正确顺序：

1. 主会话先写数据表和 API 契约
2. 子线 A 先完成用户扩展与权限
3. 子线 B 和子线 C 可以并行
4. 子线 D 等文件底座和权限稳定后再接入
5. 最后统一联调通知与部署

### 10.4 Claude Code 会话模板

建议你每次都用固定模板开任务，不要临场想到什么说什么。

主会话模板：

- 目标模块
- 当前依赖
- 不允许改动的文件
- 要新增的文件
- 要复用的现有模块
- 验收标准

子会话模板：

- 你只负责哪个模块
- 上游接口是什么
- 下游页面或接口是什么
- 不要改哪些公共文件
- 完成后输出哪些自测结果

### 10.5 Git 协作建议

后续真正开始写代码时，建议这样做：

- 主分支只保留稳定代码
- 每个模块一个功能分支
- 每个模块一个独立 worktree
- 先接口对齐，再并行改代码
- 合并前先跑模块自测，再跑总联调

推荐分支命名：

- `feature/office-agent-base`
- `feature/office-agent-meeting`
- `feature/office-agent-report-task`
- `feature/office-agent-file-qa`
- `feature/office-agent-notify`

## 13. 部署方案定稿

### 13.1 是否需要服务器

如果只是你自己本机临时演示，可以先本地跑。

但只要你准备给公司内部多人使用，就建议部署到一台固定 Linux 服务器，不要长期跑在个人电脑上。

### 13.1.1 WSL 和 Windows 使用关系

WSL 只是你的开发环境，不是最终用户的使用环境。

也就是说：

- 你现在可以继续在 WSL 里开发
- 最终项目部署到 Linux 服务器或 Windows 服务器都可以
- 你的同事在 Windows 电脑上只需要用浏览器访问系统地址即可
- 他们不需要安装 WSL，也不需要懂 Linux

你可以把它理解成：

- WSL 是开发工具
- 浏览器是使用入口
- 服务器才是正式运行环境

所以这件事没有问题，后面完全可以做到“你在 WSL 开发，团队在 Windows 上访问使用”。

### 13.2 一期推荐部署方式

推荐方案：

- 1 台 Linux 服务器
- Docker 部署
- 内网访问
- 继续使用云端模型 API

推荐最低配置：

- 4 核 CPU
- 8G 内存
- 100G SSD

更稳妥配置：

- 8 核 CPU
- 16G 内存
- PostgreSQL 与 Redis 分开管理

### 13.3 是否要买 GPU 服务器

一期不需要。

只要你不是本地自部署大模型，而是继续调用 Claude、OpenAI 或国内模型 API，就不需要 GPU 服务器。

### 13.4 通知渠道优先级

当前建议固定为：

1. 系统内工作台提醒
2. 邮件提醒
3. 企业微信或飞书

不建议一期把“普通微信群自动精准推送”当主目标，原因是：

- 普通微信生态开放能力差
- 自动化限制多
- 个人号和群聊消息都不适合作为企业系统主链路

如果后面公司愿意配企业微信或飞书，再接入会顺很多。

## 14. 风险与改进建议

### 14.1 最大风险

最大风险不是技术本身，而是一期范围失控。

最容易失控的地方有 3 个：

1. 想把所有表都做成自然语言可改
2. 想把所有消息都直接推到普通微信
3. 想一步做成完整 OA 平台

这 3 个都不建议在一期扩进去。

### 14.1.1 精简裁剪的风险

第二个高风险点是“过早删原生模块”。

要避免这 3 种删法：

1. 还没理清依赖就直接删后端应用
2. 前端入口没关完就删接口
3. 数据表还在被引用时就直接清库

正确做法是两阶段裁剪：

- 第一阶段：隐藏无关入口，先让新项目界面变干净
- 第二阶段：等办公 Agent 主链路稳定后，再删无用源码和依赖

### 14.2 最值得优先打磨的亮点

最能体现业务价值的演示顺序建议是：

1. 会议转写一键变纪要
2. 纪要任务自动进入任务池
3. 日报自动汇总成个人任务状态
4. 测试报告直接问答并打开原文件
5. 出入库表一句话查询和一次受控修改

### 14.3 二期方向

等一期稳定后，再考虑下面这些增强项：

- 企业微信或飞书提醒
- 多张业务表统一接入
- 更细的权限和部门隔离
- 更多报表视图
- 会议录音直传和自动转写
